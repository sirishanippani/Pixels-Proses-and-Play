# Project Description

## 2.1 Overview

Pixels, Proses & Play is a web-based blogging platform developed as the applied project for the Scaler Neovarsity Backend Specialization. The platform supports three user roles: anonymous readers who can browse published content without creating an account, registered authors who can publish and manage their own posts, and an administrator responsible for moderation of the user base and the post catalogue. Registration is open to new authors, and the author community grows through direct invitation rather than public promotion. The platform is intended to serve a close-knit writer and reader group that shares an interest in long-form personal writing, software notes, and short cultural pieces.

The system is implemented in Java 17 on the Spring Boot 3.4 framework. Server-side rendering is handled by the Thymeleaf template engine, with Spring Security providing form-based authentication and BCrypt password hashing. Persistence is managed by Spring Data JPA over Hibernate, with PostgreSQL as the production database and H2 as the database used during local development and automated testing. The database schema is owned by Flyway, which applies versioned migrations at application startup and validates that the deployed entities match the schema expected by the application code. The user interface relies on Bootstrap 5 for its layout primitives and on a custom stylesheet built against CSS custom properties for colour, typography, and spacing decisions.

The system follows a classical three-layer backend architecture. Incoming HTTP requests are received by Spring MVC controllers, which delegate business logic to a service layer. The service layer encapsulates the business rules, coordinates transactions, and invokes the repository layer, which is responsible for data persistence through Spring Data JPA. Each controller accepts only primitive types, form Data Transfer Objects (DTOs), or the authenticated user principal as input. No controller writes to the database directly. The separation ensures that validation, authorization, and transaction boundaries are enforced in predictable locations, and that the controllers can be tested in isolation without exercising the full database stack.

A representative request flow is the retrieval and display of a single blog post. The browser issues a GET request to the URL `/post/{id}`. The request is received by the `PostController`, which calls the `PostService.getPostForView(id)` method. The service method invokes the `PostRepository.findById(id)` method, which has been overridden in the project to attach an `@EntityGraph` fetch plan covering the post author and tag collection. The repository executes a single SQL join that retrieves the post along with its author and tags. The service returns the loaded entity to the controller, which places it in the view model and resolves the `post_detail.html` Thymeleaf template. The template renders the post title, author byline, tag chips, sanitized HTML body, and comment section. If the post identifier does not exist, the service throws a `PostNotFoundException` annotated with `@ResponseStatus(HttpStatus.NOT_FOUND)`, and Spring maps the exception to the custom 404 template.

The project was developed as a phased refactor of an earlier prototype. The prototype was functional but exhibited several defects typical of a first implementation, including entity leakage from the controllers to the views, implicit schema generation from entity bytecode, and insufficient separation between validation and persistence. The refactor was organised into seven phases, each addressing a distinct engineering concern and each producing a committable working build. The phases are summarised in Section 2.5 and treated in detail in Chapter 6.

## 2.2 Motivation

The platform was developed for two reasons. The first is practical and concerns content ownership and platform independence. The second is academic and concerns the suitability of a blogging platform as a vehicle for exercising a modern backend stack.

The practical motivation starts from a limitation of commercial publishing platforms. Writers who use platforms such as Medium, Substack, or hosted WordPress face three recurring forms of friction. First, the writer does not own the rendering surface. The platform determines typography, color, whitespace, and the overall reading experience, and the writer has limited ability to shape how a post is presented. Second, the platform's monetization and editorial policies influence which posts are surfaced to readers. A post that fits the platform's engagement model is amplified; a post that does not is not. Third, the writer's archive is governed by the platform's data retention, export, and account policies. A change in those policies, or the eventual shutdown of the platform, can impair access to the writer's own work. A self-hosted platform eliminates all three forms of friction at the cost of operating the platform. The project chooses to pay that cost, both because the operational cost is small for a personal deployment and because the operation itself is instructive.

The academic motivation starts from the specific requirements of a backend capstone report. A capstone project must demonstrate competence across a range of production engineering practices, including input validation, authentication and authorization, schema design and evolution, transaction management, input sanitization, file upload hygiene, deployment, and observability. A trivial CRUD application does not justify the architectural separations that a production codebase requires, because the simple cases rarely expose the faults that those separations prevent. A large distributed system imposes operational overhead unsuited to a single-author capstone. A blogging platform occupies a useful middle ground. It combines authenticated write paths with public read paths, structured post data with user-submitted HTML, a simple role-based authorization model, a persistent file object model for profile images, and a schema that evolves as features are added. Each of these concerns provides a natural setting for applying an industry-standard pattern, and each concern can be exercised meaningfully without introducing the complexity of a microservice topology.

Other candidate subjects were considered during the project proposal phase. An e-commerce platform would have offered rich inventory, order, and payment flows, but would have required integrating with external payment providers whose sandboxes change frequently and whose behavior would be difficult to document in a report. A discussion forum would have offered interesting authorization problems around thread-level permissions, but would have duplicated much of the comment infrastructure of the blogging platform while offering little that the blogging platform does not. A task tracker would have offered relational modelling practice through parent and child tasks, labels, and assignments, but lacked the user-submitted HTML and file upload concerns that motivate the sanitization and upload service seams in the current project. The blogging platform was chosen as the subject because it exercises the broadest range of the Specialization's topics while remaining within the time and operational budget of a single-author capstone.

The project is intentionally not an attempt to build a competitor to any commercial platform. Its workload is small, its audience is private, and its author is the same person operating the server. The capstone context frames the project as a representative study of production engineering practices, rather than as a deployment at scale.

## 2.3 Objectives

The project pursues two sets of objectives. The product objectives describe the capabilities offered to users of the platform. The engineering objectives describe the practices the codebase is designed to exemplify. The two sets are developed in parallel, and each engineering objective is treated in detail in a later chapter.

### Product Objectives

1. **Authored post lifecycle.** Allow a registered author to compose, edit, and delete rich-text blog posts. The post composition surface supports formatted text, headings, lists, links, images, and inline code. The author may associate each post with an arbitrary number of tags, which are created on first use. The author may edit any post they own at any time, and may delete any post they own.
2. **Reader browsing.** Allow anonymous readers to browse the catalogue of published posts through the homepage. The homepage displays recently published posts and a small set of featured posts. Readers may open any post and view the full content, including the author byline, tag list, and comment section. A title-based search surface allows readers to locate posts by keyword without creating an account.
3. **Comments.** Allow authenticated users to leave comments on posts and to delete their own comments. Comments appear below the post content and are displayed in chronological order. The platform does not support threaded replies or reactions on comments; both are listed as out-of-scope capabilities in Section 2.4.
4. **Author profiles.** Allow each author to maintain a public profile page containing the author's chosen display name, a short biography, and a profile image. The profile page lists all posts published by that author in reverse chronological order.
5. **Moderation.** Provide an administrator with a console through which users and posts can be inspected and removed. The administrator can delete any user account or any post. The administrator can also change the role of another user between the author and administrator roles.

### Engineering Objectives

1. **Explicit service seams.** Separate the transport, business, and persistence layers through explicit service interfaces. No controller holds business logic. No controller writes to the database directly. Services accept primitive parameters or form DTOs as input and return domain entities or projections. The separation is treated in detail in Chapter 6 (Feature Development Process), where the full request flow for a representative write endpoint is described.
2. **Structural prevention of mass assignment.** Replace framework-shaped input bindings on controller methods with form DTO records whose fields enumerate exactly the attributes the submitting audience is permitted to write. Each form DTO excludes identity fields that are provided by the path or the authenticated principal, and excludes privileged fields such as roles. The approach is treated in detail in Chapter 6.
3. **Schema as code.** Declare the database schema as versioned SQL migrations managed by Flyway, with Hibernate configured to validate rather than modify the schema at startup. Support three database vendors (H2, MySQL, PostgreSQL) from the same application code, with the schema expressed in vendor-specific native syntax under Flyway's `{vendor}` placeholder. The approach is treated in detail in Chapter 5 (Database Schema Design).
4. **Service seams for cross-cutting concerns.** Isolate cross-cutting infrastructure behind thin service seams. File upload validation is encapsulated by a dedicated storage service that enforces an allowlist-based MIME policy and writes files under UUID-derived names. HTML sanitization is encapsulated by a dedicated sanitizer service that applies an OWASP-compliant policy on write. User-facing copy and flash feedback are encapsulated by a flash service backed by Spring's `MessageSource`. Each is treated in detail in Chapter 6.
5. **Design tokens as single source of truth.** Build the view layer against a stylesheet in which every color, typographic, spacing, and radius decision is declared once as a CSS custom property on `:root` and consumed by every component rule through a `var()` reference. Light and dark themes are implemented as redefinitions of the same tokens rather than as separate stylesheets. The approach is treated in detail in Chapter 8 (Technologies Used).
6. **Free-tier deployment.** Deploy the application to a free-tier managed platform without compromising the security, portability, or maintainability properties established in earlier phases. The deployment target is Render for the web service and Neon for the managed PostgreSQL instance. The approach is treated in detail in Chapter 7 (Deployment Flow).

## 2.4 Scope

The scope of the project was shaped by two considerations. The first is the capstone context, which requires a complete working deliverable within a bounded time budget. The second is the engineering focus of the report, which treats the codebase as a demonstration of production practices rather than as a deployment at scale. Capabilities that would expand the surface area of the platform without exercising additional engineering practices were excluded.

### In Scope

- **Rich-text post authoring.** Post composition is supported through the Toast UI editor in WYSIWYG mode. The editor outputs HTML that is sanitized on the server before persistence.
- **Three user roles.** Anonymous reader, registered author, and administrator. Each role is defined by its authorization scope and its view of the application.
- **Tag taxonomy.** Posts can be tagged with an arbitrary number of comma-separated tags. Tags are created on first use and reused on subsequent posts.
- **Flat comments.** Posts support a flat comment list below the post content. Each comment has an author, a timestamp, and a text body.
- **Author profiles.** Each registered author has a public profile page containing display name, biography, and profile image.
- **Title-based search.** A client-side search field issues JSON requests to a search endpoint, which returns matching post titles for display as a dropdown.
- **Administrator moderation.** The administrator console displays all users and posts, with controls to delete or to change user roles.
- **Theme-aware design system.** A single stylesheet built against CSS custom properties supports both light and dark themes. A decorative botanical background is served by a single PNG asset and re-tinted per theme.
- **Internationalisation-ready copy.** All user-facing flash messages are externalized to a `messages.properties` file consumed through Spring's `MessageSource`. Translation to another locale is a matter of adding a second properties file.
- **Free-tier cloud deployment.** The application is containerized with Docker and deployed to Render as a free-tier web service, with a managed PostgreSQL instance on Neon.

### Out of Scope

- **Multi-tenant hosting.** The platform hosts a single author community. Isolated namespaces for multiple independent organizations are not supported. The schema is not partitioned by tenant.
- **Threaded or nested comments.** Comments are flat. Replies to comments are not supported. Reactions such as likes or emoji responses are not supported.
- **Media library.** Each post's inline images are uploaded at authoring time and are not organized into a reusable library. There is no cross-post image referencing.
- **Newsletter integration.** The platform does not send email notifications for new posts, nor does it support reader subscriptions over email.
- **Analytics and tracking.** The platform does not record reader behaviour. Page visit counts, scroll depth, referrer analytics, and author dashboards are not implemented.
- **Public REST or GraphQL API.** All functionality is exposed through the server-rendered Thymeleaf interface. No API is published for use by mobile clients or third-party integrations.
- **Real-time features.** The composition surface does not provide collaborative real-time editing. The reading surface does not stream updates when a new post is published.
- **Server-side rendering optimizations for search engine crawlers.** Open Graph metadata, structured data, and sitemap generation are out of scope for the current project.

Each excluded capability is a legitimate feature of a production blogging platform. Each would either expand the operational surface in ways unsuited to a single-author deployment, or would duplicate engineering practices already demonstrated by the in-scope capabilities. Future work on the platform could add any of them individually without disturbing the existing architecture.

## 2.5 Project Development Process

The project was developed in seven numbered phases, each addressing a distinct engineering concern. Within each phase, the work was further decomposed into smaller slices, each producing a committable working build. The phases run in sequence, but the build remains functional at every intermediate point. This approach is a deliberate application of the strangler-fig refactoring pattern, in which an existing system is modified incrementally behind a thin interface rather than rewritten in one step.

Figure 2.2 shows the overall development pipeline. Each box represents a phase. Each phase produces an artifact that is consumed by the subsequent phases. The arrows indicate the dependency between phases; the dashed arrow from Phase 2 to Phase 6.5 indicates that the design-tokens stylesheet in Phase 6.5 depends on the view DTO separation first established in Phase 2.

### Phase 1: Safety Net

The first phase introduced a local test profile backed by H2 in MySQL compatibility mode, along with a small suite of integration tests. The tests cover the public homepage, the authenticated dashboard, the login and registration endpoints, and a representative read of a post. The purpose of the phase is to produce a regression safety net that can be run in milliseconds and that detects breakage from any subsequent structural change. Six tests were added in this phase. The artifact of Phase 1 is a green baseline against which every later phase measures its correctness.

### Phase 2: Data Shape Separation

The second phase introduced Data Transfer Object records and a set of dedicated mapper components to separate the entity model from the view model. Prior to this phase, the Thymeleaf templates read directly from JPA entities, which exposed the entity collection to template-time mutations. Under Spring Boot's default Open Session In View configuration, such mutations were persisted silently at session close. The symptom was intermittent corruption of post content on the homepage. The fix was to introduce a `PostSummaryDto` record containing only the fields the template requires, and a `PostSummaryMapper` component that centralised the HTML stripping, text truncation, and tag sort order used to construct the DTO. The `HomeController` and `DashboardController` were migrated to construct DTOs from the service results before passing them to the view. A regression test was added as a forward-looking invariant: visiting the homepage must not mutate post content. The defect is described in detail in Section 2.6 and its root cause is traced through Chapter 6.

### Phase 3: Service Layer Extraction

The third phase extracted the business logic from the controllers into a set of service classes. A `PostService`, `TagService`, `CommentService`, `AdminService`, and `UserService` were introduced. Each controller was migrated in a separate commit, following the strangler-fig pattern: for the duration of the phase, the codebase existed in a mixed state in which some controllers used the service seam and some still used the repository directly. The service methods accept primitive parameters rather than JPA entities. This design choice structurally confines mass-assignment risk: even if an attacker crafted an HTTP form containing fields that should not be writable, those fields cannot cross the service seam, because the service does not accept entity-shaped input. A dedicated exception package was added to hold the domain exceptions introduced by the phase, including `PostOwnershipException`, `PostNotFoundException`, `CommentOwnershipException`, and `UserNotFoundException`. Not-found exceptions were annotated with `@ResponseStatus(HttpStatus.NOT_FOUND)` so that Spring would map them to the custom 404 page directly, while ownership exceptions were caught by the controller and translated to a redirect with a flash message.

### Phase 4: Form DTOs and Bean Validation

The fourth phase closed the mass-assignment risk at the input binding level. Every write endpoint was migrated to accept a form DTO record as its `@ModelAttribute` input, instead of a JPA entity. Four form DTOs were introduced: `RegisterRequest`, `PostForm`, `ProfileForm`, and `CommentForm`. Each DTO enumerates exactly the fields the submitting audience is permitted to write. A field that appears on the entity but not on the form DTO is silently dropped by the Spring binder, which is the desired behavior. Validation rules were expressed through Jakarta Bean Validation annotations on the DTO fields, and enforced by the controller through the `@Valid` annotation and the `BindingResult` parameter. A custom validation constraint, `@NotBlankHtml`, was introduced to handle the WYSIWYG editor's empty-shell output, which contains tags such as `<p><br></p>` and which the standard `@NotBlank` constraint would accept as non-empty. Validation failures are displayed inline on the form through Thymeleaf's `th:errors` attribute, and the comment form uses the Post-Redirect-Get idiom with a flashed binding result to survive the redirect back to the post page.

### Phase 5: Portability

The fifth phase replaced Hibernate's inferred schema generation with versioned Flyway migrations. The `spring.jpa.hibernate.ddl-auto` setting was changed from `update` to `validate`, which causes Hibernate to verify that the deployed entities match the schema expected by the application code and to fail loudly on mismatch rather than silently altering the schema. Flyway was configured with the `spring.flyway.locations=classpath:db/migration/{vendor}` property, where `{vendor}` is resolved at startup to the detected database vendor. Three parallel baseline migrations were written, one each for H2, MySQL, and PostgreSQL, each expressed in the vendor's native syntax. A native vendor-locked query for random post selection, which used MySQL's `ORDER BY RAND()` function, was replaced by a portable JPQL query that returns all post identifiers, followed by an in-memory `Collections.shuffle` call in Java, followed by a second portable query that fetches the selected posts by identifier. The `comment` table was renamed to `comments` through the `@Table` annotation on the entity, so that the table name clears PostgreSQL's reserved word list.

### Phase 6: Security and Hygiene

The sixth phase hardened the codebase against several classes of risk and removed remaining debug surface. Open Session In View was disabled through the `spring.jpa.open-in-view=false` property, which closes the Hibernate session at the end of the service transaction rather than at the end of the HTTP response. The consequence is that any attempt to access a lazy association from within a template now fails with a visible `LazyInitializationException`, which forces the service to install an explicit fetch plan. Three repository methods were overridden to attach `@EntityGraph` fetch plans: `PostRepository.findById`, `PostRepository.findAll`, and `CommentRepository.findByPost`. A dedicated `StorageService` was introduced to encapsulate file upload handling, with an allowlist-based MIME policy (`image/jpeg`, `image/png`, `image/webp`), UUID-derived filenames, and file extensions derived from the whitelisted content type rather than from the client-supplied filename. A dedicated `HtmlSanitizer` service was introduced to apply an OWASP-compliant sanitization policy to all post content on write, so the database holds only allowlisted markup. A debug endpoint `/whoami` was removed, along with an unused test template. The `.gitignore` file was rewritten, which fixed a prior bug that had been silently excluding `application.properties` from version control.

### Phase 6.5: User Interface Polish

The intermediate Phase 6.5 was dedicated to the user interface. The stylesheet was rebuilt against CSS custom properties organized into a four-lane semantic palette: a rose tone for serif headings, a lavender tone for calls to action, a mint tone for references to people, and a peach tone for pulled quotes. Light and dark themes were implemented as redefinitions of the same tokens rather than as separate stylesheets. All user-facing copy was centralized in a `messages.properties` file consumed through a thin `FlashService` wrapping Spring's `MessageSource`. A shared Thymeleaf fragment, `fragments/head.html`, was introduced to hold the font and stylesheet declarations required by every page. A decorative botanical background was added, served by a single transparent PNG asset applied through the `body::before` pseudo-element and re-tinted per theme using a CSS filter chain. A dark-mode browser autofill bug in Chrome, which had been rendering password fields with a bright background in dark mode, was fixed through the standard `-webkit-box-shadow` inset workaround.

### Phase 7: Deployment

The seventh and final phase targets the deployment of the application to a free-tier managed platform. The Spring Boot application is containerized with a Dockerfile that uses the `eclipse-temurin:17-jre-alpine` base image and configures the JVM with `-XX:MaxRAMPercentage=75.0` so that memory usage respects the container's resource limit. The container is deployed to Render as a free-tier web service. The database is a managed PostgreSQL instance on Neon, also on a free tier. A `/health` endpoint is exposed for use by UptimeRobot, which pings the endpoint every fourteen minutes to prevent Render's idle-shutdown policy from spinning down the container. Database credentials and other secrets are provided as environment variables through Render's configuration surface rather than committed to the repository. Phase 7 is in progress at the time of writing and is treated in detail in Chapter 7 (Deployment Flow).

## 2.6 Key Challenges Addressed

Three defects encountered during development illustrate the kinds of fault that an incremental refactor behind a thin interface is able to surface and repair. Each is described in summary form below and treated in detail in Chapter 6.

### The Post-Content Corruption Defect

The symptom of the defect was observed on the homepage. After several page refreshes, the body of some posts on the homepage would be replaced by their truncated summary. The behaviour was intermittent and could not be reproduced reliably in a single pass. The affected posts were not restricted to any particular author, tag, or date.

The diagnostic process started from the symptom and followed the data flow backward through the application. The homepage controller was reading the ten most recent posts through the repository, placing them into the view model, and resolving the `index.html` template. The template was iterating over the posts and displaying a truncated summary for each. The truncation was being computed by a method defined on the post entity, which modified the entity's own content field to the truncated value as a side effect of computing the return value. In isolation, the mutation would be discarded when the request completed. Under Spring Boot's default Open Session In View configuration, however, the Hibernate session remained open for the duration of the template rendering. At session close, Hibernate observed that the entity was dirty and persisted the mutation to the database, overwriting the original post content with the truncated summary.

The fix introduced a `PostSummaryDto` record containing only the fields the template requires, and a `PostSummaryMapper` component that computes the truncated summary into the DTO rather than into the entity. The homepage controller now constructs a list of DTOs from the repository result before passing it to the template. The template iterates over DTOs, which are immutable records, and cannot therefore be mutated as a side effect of rendering. A regression test was added as a forward-looking invariant: visiting the homepage must not mutate post content. The defect is described in detail in Chapter 6.

The broader category of fault is the exposure of managed JPA entities to templates under the default Open Session In View configuration. The fix generalizes to a rule: list views are rendered from DTOs, and entities do not cross the boundary between the service and the view layer except in detail views where mutation is expected.

### The Hidden N+1 Under OSIV

The symptom of the second defect was not a functional bug but a performance pattern. A SQL log capture of a homepage load revealed that the server issued twenty-one queries per page view: one to load the ten most recent posts, and one additional query per post to load the tag collection. The additional queries were not logged by the application and did not appear in any profiling report run against the service layer. They were being triggered by the template's iteration over `post.getTags()`, which forced Hibernate to resolve the lazy association for each post individually.

The diagnostic process followed the Open Session In View investigation already underway during Phase 6. Disabling the OSIV filter did not fix the N+1 directly, but it made the defect visible. Instead of silently issuing additional queries during rendering, the template now raised a `LazyInitializationException` on the first access to a lazy association after the service transaction had closed. The exception's stack trace named the exact template line and the exact repository method that needed a different fetch plan.

The fix overrode the `findTop10ByOrderByCreatedAtDesc` method in the `PostRepository` interface to attach an `@EntityGraph(attributePaths = {"user", "tags"})` annotation. The annotation instructs Hibernate to load the author and tag associations eagerly in the same SQL query that loads the posts themselves. The query count dropped from twenty-one to one. Similar annotations were added to the `findById`, `findAll`, and `findAllById` methods, each targeting the association set that the corresponding template requires.

The broader category of fault is the silent N+1 under OSIV. Disabling OSIV surfaces the fault as a visible exception, which is itself the fix for a broader class of latent performance problems. Chapter 6 documents the full set of repository method overrides added during Phase 6.

### Mass-Assignment at the Registration Endpoint

The symptom of the third defect was not observed in production; the defect was identified during a routine review of the registration controller. The controller's `register` method accepted a `User` JPA entity as its `@ModelAttribute` input. The Spring binder populates the entity's fields by matching the names of HTTP form parameters to the setter methods on the entity. The `User` entity has a `role` field, which is the field used by Spring Security to determine the user's authorization. An attacker who inspected the HTTP form and crafted a request containing a `role=ROLE_ADMIN` parameter would have had that value bound to the entity by the binder and persisted by the repository, giving the attacker administrator access.

The fix was applied in two independent phases. Phase 3 introduced the service seam. The `UserService.register` method accepts primitive parameters (`username`, `email`, `password`) rather than a `User` entity. The service constructs the entity internally, sets the role to `ROLE_USER` unconditionally, encodes the password with BCrypt, and persists the entity. Even if an attacker successfully bound a `role` field to the entity at the controller layer, the field value would not cross the service seam. Phase 4 then closed the risk at the binding layer by introducing the `RegisterRequest` form DTO. The DTO contains only the `username`, `email`, and `password` fields. A `role` parameter in the HTTP form is silently dropped by the binder, because the DTO has no `role` field.

The broader category of fault is mass assignment on write endpoints. The fix generalizes to a rule: every write endpoint accepts a form DTO whose fields enumerate exactly the attributes the submitting audience is permitted to write, and the service accepts primitives rather than entities. The two defences are redundant by design: either defence alone would close the registration-endpoint defect, but having both prevents a future regression in one layer from re-opening the vulnerability.

Each of the three defects is representative of a broader category of fault that production codebases routinely encounter. The design choices made in response are revisited in Chapters 5 and 6, where the full implementation of each fix is traced through the codebase.
